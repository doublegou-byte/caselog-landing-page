# 标准更新流程

适用场景：

- 已经有 GitHub Actions 自动构建镜像
- 已经有阿里云镜像仓库
- 腾讯云服务器上已经跑着 `gateway + web`
- 当前更新的是前端静态官网镜像

这份文档只讲“怎么稳定更新线上版本”，不讲第一次部署。

当前线上基线：

- `www.caselog.cn` 已启用 HTTPS
- `caselog.cn` 会统一跳转到 `https://www.caselog.cn`
- `api.caselog.cn` 已纳入同一张 HTTPS 证书，当前返回 `503`
- 服务器上的前端镜像版本已经升级到 `1.0.1`
- 证书由 `acme.sh + DNSPod API` 自动签发和自动续期

## 1. 总体原则

推荐把更新流程固定为两段：

1. 推送到 `main`：只做构建校验，不推镜像
2. 推送版本 Tag：构建并推送正式镜像

这样可以把“代码合并”和“正式发布”分开，避免每次提交 `main` 都直接影响线上。

## 2. 标准发布顺序

每次发布建议按这个顺序走：

1. 在本地完成代码修改
2. 提交到 `main`
3. 等 GitHub Actions 的 build-only 检查通过
4. 打发布 Tag，例如 `v1.0.1`
5. 等 GitHub Actions 推出正式镜像
6. 到服务器把镜像 tag 改成新版本
7. 在服务器执行 `docker compose pull && docker compose up -d`
8. 验证线上是否正常

## 3. 本地发版命令

先提交并推送 `main`：

```bash
git add .
git commit -m "release prep: 1.0.1"
git push origin main
```

确认 GitHub Actions 的 build-only 通过后，再打 Tag：

```bash
git tag v1.0.1
git push origin v1.0.1
```

## 4. GitHub Actions 会做什么

当前工作流规则：

- 推送到 `main`：只构建，不推镜像
- 推送 `v1.0.1`：构建并推送正式镜像

发布 `v1.0.1` 后，通常会生成这些标签：

- `1.0.1`
- `1.0`
- `latest`
- `sha-<commit>`

线上部署建议优先使用固定版本号，例如 `1.0.1`，不要长期直接依赖 `latest`。

## 5. 服务器怎么更新

假设服务器当前跑的是旧版本，比如：

```yaml
image: crpi-had8j9la06ibxzbx.cn-shanghai.personal.cr.aliyuncs.com/three_engine/caselog-web:1.0.0
```

发布新版本后，把它改成：

```yaml
image: crpi-had8j9la06ibxzbx.cn-shanghai.personal.cr.aliyuncs.com/three_engine/caselog-web:1.0.1
```

然后在服务器执行：

```bash
cd /opt/caselog
docker compose pull
docker compose up -d
docker compose ps
```

## 6. 服务器验证命令

更新后先看容器状态：

```bash
docker compose ps
docker logs caselog-gateway
docker logs caselog-web
```

再做本机请求验证：

```bash
curl -I http://www.caselog.cn
curl -I https://www.caselog.cn
curl -I https://caselog.cn
curl -I https://api.caselog.cn
```

如果这次更新包含了“未知路径返回 404”的修复，还可以额外验证：

```bash
curl -I https://www.caselog.cn/wp-admin/setup-config.php
```

预期应该返回：

- `http://www.caselog.cn` -> `301` 到 `https://www.caselog.cn`
- `https://www.caselog.cn` -> `200`
- `https://caselog.cn` -> `301` 到 `https://www.caselog.cn`
- `https://api.caselog.cn` -> `503` 或你当前 API 的真实返回
- `/wp-admin/setup-config.php` -> `404`

## 7. 回滚流程

如果新版本有问题，不要在服务器临时改配置逻辑，直接回滚镜像版本。

例如把：

```yaml
image: crpi-had8j9la06ibxzbx.cn-shanghai.personal.cr.aliyuncs.com/three_engine/caselog-web:1.0.1
```

改回：

```yaml
image: crpi-had8j9la06ibxzbx.cn-shanghai.personal.cr.aliyuncs.com/three_engine/caselog-web:1.0.0
```

然后执行：

```bash
cd /opt/caselog
docker compose pull
docker compose up -d
```

## 8. 证书续期和应用发版是两条线

当前线上证书不再靠“腾讯云控制台下载证书包再手动上传”维护，而是由服务器上的 `acme.sh` 直接负责：

- DNS 验证方式：`dns_dp`
- 域名：`caselog.cn`、`www.caselog.cn`、`api.caselog.cn`
- 安装目标：
  - `/opt/caselog/deploy/gateway/certs/web/caselog.cn_bundle.pem`
  - `/opt/caselog/deploy/gateway/certs/web/caselog.cn.key`
- 续期后自动执行：
  - `docker exec caselog-gateway nginx -s reload`

这意味着：

- 前端镜像发版不需要重新处理证书
- 证书续期也不需要重新发布前端镜像
- 两者应分开维护

如果你只是发布前端新版本，这份文档里的标准镜像更新流程就够了。

## 9. 不推荐的做法

为了让线上行为可追踪，尽量避免这些做法：

- 不建议直接在服务器里改前端源码再构建
- 不建议长期部署 `latest` 而不记录版本
- 不建议每次推 `main` 都自动覆盖线上
- 不建议线上出问题后临时修改容器内部文件
- 不建议再回到“手动下载证书包并覆盖线上文件”这条路径，除非你明确放弃 `acme.sh` 自动续期

更稳定的方式是：

- 改代码
- 合并到 `main`
- 打 Tag 发版
- 服务器更新固定版本号
- 有问题就回滚到上一个固定版本号
